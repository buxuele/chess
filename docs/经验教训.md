# 经验教训

2026-10-28 国际象棋项目的返工复盘。开发过程明细见项目根目录 开发记录.md，既有偏好基准见 docs/用户偏好.md，本文只沉淀本轮新确认的事实与可执行规则。

## 一、开发过程回顾

1. 桌面端从 chess 项目拆出为独立项目 chess-desktop，just_run.sh 默认启动网页版。
2. 界面经历多轮精简：删顶栏标题、删玩家名字、删 棋谱 入口、删坐标标注、删状态标签、删被吃棋子展示条，最终主界面只剩棋盘与右上角 设置、新对局 两个按钮。
3. 棋子移动从闪现改为滑动，历时三轮：先调时长（0.5 秒、1.2 秒），再查真因，最后发现是系统「减弱动态效果」把动画整个禁用，与时长无关。
4. 交互修正：新对局删掉两段确认，单击生效；启动不再自动恢复上一局。
5. 动画大扫荡：删落子弹跳（pieceIn）、提示点呼吸（hintPulse）、将军红光呼吸（checkPulse）、入场浮起（rise）、弹窗渐隐（fadeIn）、提示条渐变（toast transition），只保留棋子滑行一个动画。
6. 桌面版因反复干扰被弃用，已构建产物删除，源码保留在 chess-desktop。

## 二、用户偏好总结

1. 简洁是硬标准：界面元素必须要么承载信息、要么承载操作，其余全删。用户会持续施压直到界面真正干净，不要用保守解释去应付。
2. 极简要一次到位：用户明确批评「我说一句你删一个」的挤牙膏式修改。接到删减需求时，应全局盘点同类元素与关联元素，一次清完。
3. 核心操作一键到底：不接受任何形式的两段确认、防误触拦截。
4. 体感必须真实可见：动画要人眼能看清过程，速度参数要让用户可调，不接受默认值拍脑袋。
5. 反对多余交互：不要编号选项、不要中途反问方案，拿不准的语义（如「底部的标题」）先问清再动手。
6. 进程零残留：由助手启动的服务，任务结束必须按进程号关闭，端口还要顺手核对。
7. 文档全中文、无 emoji、无花哨排版；重要结论要有可复现的数字或命令输出佐证。

## 三、经验教训

1. 动画失效先查系统无障碍设置：macOS「减弱动态效果」开启时，matchMedia('prefers-reduced-motion: reduce') 为 true，任何依赖该开关的功能都会被静默跳过。本轮闪现的真因即此，与动画时长无关。排查体感问题先读 `defaults read com.apple.universalaccess reduceMotion`。
2. 无头浏览器的验证结果不可直接当作用户环境的结论：它继承同样的系统设置，还原不了用户看到的画面；涉及视觉与体感的验证，要么在页面内逐帧采样数据，要么与用户确认现象。
3. 共享资源的下游产物要同步重建：桌面壳的网页资源是构建时快照，改了网页不改产物，用户看到的就是旧版。改完共享资源必须枚举并重建所有依赖方。
4. 删 DOM 元素必须全局搜引用：本轮删除 strips 的 root 字段后，hideResult 里残留 strips.bottom.root 调用，页面初始化直接崩溃（Cannot set properties of undefined）。删除字段、类名、ID 前先 grep 全部引用点，删完跑一次真实页面。
5. 审美类需求按终点做：用户给出的删减指令背后通常有一个「最终干净状态」，应该一次推到终点，而不是每轮只做最保守解释。
6. 体感参数不要自定数值：时长、字号、颜色这类主观参数，第一版就给三档可调或直接询问期望值，否则必返工。
7. 被打断的任务要回头补自检：新指令进来前，先把当前改动收尾（语法检查、残留引用、运行验证），否则容易带着半成品进入下一轮，甚至改坏共享对象结构。
8. 服务进程用完即关：启动前记录端口与进程号，验证完立即关闭并复查端口区间，避免残留进程占用端口导致下次启动漂移。
9. 每轮改动收尾三件套：语法检查（node --check）、真实浏览器验证（console 无报错 + 关键交互脚本注入）、两套测试（19、17 项）。

## 四、沟通协议

用户喜欢短句说感觉，助手需要具体指令才能不跑偏。解法不是让用户写长需求，而是助手承担翻译。

1. 用户说感觉，助手翻译成参数。听到「太暗」「太小」「太挤」，直接给终值与依据，不逐档试探。
2. 不反问，先给默认值再执行。只有真二义性时问一个二选一，不用开放式提问。
3. 用户连发多条时合并成一批，落地后逐条对照回报，不能只做最后一条。
4. 用户一个词的反馈由助手定位到具体元素与像素，不要求用户解释。
5. 每次交付三行：改了什么、验证数据、下一步。
6. 主观词先固化成数值写进 docs/用户偏好.md，定过一次就不再问。
7. 被打断时先把当前改动收尾到可运行，再切新需求。
8. 出错先给结论与修正，再补一句原因，复盘留到用户问。

## 五、React 迁移复盘

1. 背景从近黑调到深灰再调到浅灰，一共四次。教训：主观颜色第一次就该给终值或直接问清方向。
2. 「占满一屏」被理解成「留一点内边距」，先加 58 像素顶部预留，又留 8 像素。教训：满屏、贴边、占满按字面执行，不留 padding。
3. 结算卡为避开棋盘从 196 缩到 168，用户第一反应是太小。教训：终局信息是主角，几何冲突时改布局，不改字号。
4. React 迁移只对齐功能，没对齐体感，再来一局沿用 anim=null 导致瞬间闪现。教训：迁移要逐项核对动效路径，包括重置。
5. 走子时长固定 1.2 秒，与距离无关，小兵一步也要等 1.2 秒。教训：动效参数要按几何量计算，而不是按事件计算。
6. 验证前没确认服务进程与构建版本，出现旧 preview 与截图工具重置滚动导致的误判。教训：先确认端口、进程、构建 hash，再下结论。
7. 偏好文档长期写深色背景与棋盘下方结算，实现改了文档没改。教训：改完实现当轮同步文档，不留下轮返工。
8. UI 交互每次靠临时脚本验证，没有沉淀用例。教训：核心路径至少要有一份可重复执行的检查脚本。
